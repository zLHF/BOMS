# 商机管理系统 · 权限码表（V1.0）

> 定位：**前后端权限契约的单一源头（Single Source of Truth）**。
> 后续《API 接口清单》的"权限码"字段、《页面与交互矩阵》的"权限点"列、《验收测试用例》的越权场景，全部引用本表。前后端任何权限判断不得使用本表外的自定义字符串。
> 范围：仅 V1.0（阶段 0 + MVP）= M01–M10、M12、M16、M18、M19(核心)。V1.1+ 的报价/订单/费用/短信/公海运营/报表/审批/字段权限只在第 8 节占位，**不在 V1.0 实现**。
> 依据：PRD 第 3 节角色、4.4 权限模型、M04 角色权限、各模块需求号。

## 1. 设计约定

### 1.1 命名规范

```
{domain}[:{sub}]:{action}
```

- 全小写，冒号分隔，动词结尾。
- `domain`：业务域前缀（见 1.3）。
- `sub`：可选的子对象（如 `opp:follow:create`、`org:user:reset_pwd`）。
- 一个权限码 = 一个可被前端 `v-perm` 判定、被后端接口注解校验的最小动作。

### 1.2 权限码三层 + 一类不进表

| 层 | 标识 | 控制对象 | 前端落点 | 后端落点 |
|----|------|----------|----------|----------|
| 菜单权限 | `menu:*` | 模块/页面可见 | 路由 meta + 动态菜单 | 登录返回可见菜单集合 |
| 操作权限 | 各 `domain:*` 动作码 | 按钮/接口动作 | `v-perm` 指令显隐/禁用 | `@RequirePerm("code")` 注解校验 |
| 阶段权限 | `opp:stage:*` / `opp:win` / `opp:lose` | 阶段推进/回退/成交/输单 | 阶段按钮显隐 | 动作接口二次校验 + 必填校验 |
| **数据范围** | **不是权限码** | 可访问哪些数据行 | 前端不可信，仅展示 | 角色 `data_scope` 属性，服务层强制过滤（见第 3 节） |

> **字段权限（脱敏，M04-03）属于 V1.2，不在 V1.0 范围。** V1.0 不做字段级脱敏码，相关需求见第 8 节占位。

### 1.3 域前缀

| 前缀 | 域 | 级别 |
|------|-----|------|
| `platform` | 平台运营（跨租户） | 平台级（不带 tenant_id） |
| `tenant` | 租户管理 | 平台级 |
| `menu` | 菜单可见 | 租户级 |
| `org` | 组织与用户 | 租户级 |
| `role` | 角色权限 | 租户级 |
| `opp` | 商机（列表/编辑/跟进/详情/协作/阶段） | 租户级 |
| `customer` | 客户/联系人/下级客户 | 租户级 |
| `task` | 任务中心 | 租户级 |
| `file` | 附件中心 | 租户级 |
| `audit` | 审计日志 | 租户级 |
| `config` | 系统配置（阶段/编号/字典） | 租户级 |

### 1.4 表头字段说明

- **数据范围**：`是` = 该 `view` 类码的查询结果必须经服务层数据范围过滤；`-` = 不涉及行级过滤。
- **审计**：`是` = 该动作必须写 `audit_log`（含前后值），对齐 PRD M18-01。
- **PRD**：对应需求号，便于追溯。

## 3. 数据范围定义（角色 `data_scope`）

| 枚举值 | 含义 | V1.0 |
|--------|------|------|
| `SELF` | 仅本人创建/负责的数据 | ✅ |
| `DEPT` | 本部门 | ✅ |
| `DEPT_AND_SUB` | 本部门及下级部门 | ✅ |
| `TENANT` | 全租户 | ✅ |
| `DEPT_CUSTOM` | 指定部门 | ⏸ 后置（V1.2 自定义规则一并做） |
| `CUSTOM` | 自定义规则 | ⏸ 后置 |

服务层按角色 `data_scope` + 组织树（`department.parent_id`）+ 上下级关系，对所有 `view` 类查询强制追加过滤条件。**前端传入的范围参数不可信。**「下属商机/下属协作/下级客户」视图依赖 `DEPT_AND_SUB` 及以上范围 + `opp:view:sub` / `customer:view:sub` / `task:view:sub`。

### 4.6 协作授权（对象级，不进角色权限码）

商机协作的细粒度权限（仅查看 / 可跟进 / 可编辑 / 可上传附件 / 可处理任务，PRD M09-02）存储于 `opportunity_collaborator.permission_json`，**在添加协作时逐对象配置，不属于角色权限码**。**协作人员不是独立角色**（决策 D3）：任何拥有 `menu:opportunity` 的用户被添加为协作人后，即按该商机 `permission_json` 获得对象级操作权。

**判定语义（V1.0，交集方案）** —— 协作授权的本质是「扩展数据可见性 + 在该对象上收窄可用动作」，**不赋予新的动作类型权限**：

```
用户对商机 X 可执行动作 A  ⟺
    角色拥有 A 的权限码                       （动作类型，不可被协作突破）
  且 ( X 在用户数据范围内
       或 ( 用户是 X 的协作人 且 X.permission_json 允许 A ) )   （可对哪些对象行使）
```

- 推论：纯只读角色即使被授「可跟进」也**不能**跟进（缺 `opp:follow:create` 权限码）；销售被加为协作人后**能**对数据范围外的该商机跟进（可见性被扩展，动作权限本就具备）。
- 本表仅约束 `opp:collab:add` / `opp:collab:remove` 两个管理动作。

## 7. 与其他文档的引用关系

- **DDL / 数据初始化**：`role` 表、`permission` 表（`code`/`type`/`name`）、`role_permission` 关联表的初始数据直接来自本表第 4/5/6 节。`role.data_scope` 取值见第 3 节。
- **API 接口清单**：每个写接口标注 `@RequirePerm`，取值必须是本表存在的码；`view` 类接口标注是否走数据范围过滤。
- **页面与交互矩阵**：每个页面的"权限点"列只能引用本表的码。
